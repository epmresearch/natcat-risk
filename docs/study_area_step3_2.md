### Respectful Overpass access: paced retry (2026-11-22)

This version is a final controlled test of the same OSMnx/Overpass route-extraction
workflow. **Nominatim's maximum 1 request per second is a different service rule**;
Overpass does not have one universal fixed time between queries. Instead, its
per-IP slots/cooldown vary with current load and query execution time. OSMnx
already checks Overpass's server-status endpoint (`overpass_rate_limit=True`).

To avoid rapid submissions, the script also enforces **at least 30 seconds between
successive OSMnx tile download calls**, plus at most **three attempts per failed
tile**. After transient HTTP 429/502/503/504 failures it waits **30 seconds**
then **60 seconds** before the two retries. The 30-second inter-tile gap is
an intentionally conservative *project policy*, not a mandatory server-wide
interval. OSMnx may make additional underlying Overpass requests while
handling any one tile; its built-in server-status pacing remains enabled.

Successful tiles are saved independently in
`data/cache/study_area/highway99_tiles_16km_9km_v3/` and reused. This update
intentionally retains V3 cache paths, so do **not** delete caches, change the
tile geometry, or rerun multiple sessions concurrently. If the same 502 capacity
error persists after the bounded retries, stop and move to the official BC
Digital Road Atlas or an offline OSM extract rather than repeatedly hammering
the public API. Waiting cannot guarantee success when the server itself is full.

## Handling missing Highway 99 tags near Whistler

If a waypoint has no nearby H99-tagged edge, the script now compares the distance
with the **nearest drivable network edge**. If that edge is within 2.5 km, it
can be used as a clearly marked *unverified* routing anchor, and the QA report
records both distances. If even the drivable network is far away, the script
stops: verify the input geocoding, and inspect the downloaded road tiles. Only if the actual route lies outside the tiled corridor should `TILE_BUFFER_M` be adjusted, with a new cache version. Do not simply increase
the H99 snap tolerance or silently accept a route to a faraway road. Check
fallback legs, connectivity and exact highway attribution in QGIS before use.

## Method and caveats

1. Load the five geocoded corridor reference places.
2. Download the drivable network in **smaller overlapping geographic tiles** along the waypoint axis, retaining every component. Keep shared original OSM node IDs unsimplified before merging so the complete north corridor is not silently dropped.
3. Identify OSM road edges tagged as route 99 or named Sea-to-Sky Highway.
4. Prefer a nearby route-99-tagged edge for each waypoint. If none is nearby,
   and a drivable road is within 2.5 km, use it as a **clearly flagged,
   unverified fallback anchor**. This does not imply that the road is Highway 99.
5. Route through these anchor nodes on an **undirected graph**; roads tagged as Highway 99 are preferred, but unlabeled road segments may still be traversed to preserve connection.
6. Export the network-derived candidate, constituent edges, 5-km **search** buffer, QA metadata and two map previews.
7. Review length, connectivity, segment provenance and possible shortcuts/side roads. The script reports what share of routed edge length carries Highway 99 labels; low coverage is a warning, not proof that data are incorrect.

Neither 18 km nor 5 km is a scientifically selected landslide initiation/runout buffer. Those decisions belong to subsequent hazard modeling work.

## 2026-11-22: Missing Whistler roads — fix v2

The first 8-km Overpass graph contained 1,944 nodes and 4,308 edges, but both the nearest Highway 99-labeled road and nearest general drivable road were ~25.3 km from the Whistler reference point. This means the cached graph was missing Whistler's local road network, *not* merely a Highway 99 tag. A contributing cause may have been the narrow straight-waypoint corridor together with `retain_all=False`, which drops all but the largest weakly connected component (OSMnx behavior).

This v2 script therefore uses an 18-km *download* band, `retain_all=True`, and a newly named GraphML cache. It also reports the number and largest sizes of connected components. This is **not** a claim that the actual highway is contained inside any particular buffer: if the network is still incomplete, the algorithm stops and must be corrected using GIS evidence rather than fabricating an alignment.

Re-run unit tests and the main script; review the reported waypoint distances and `highway99_candidate_quality.json`. Do not upload the GraphML cache or use the candidate route for risk calculations before its geometry is checked against an independent road map.


## 2026-11-22: Overpass 502 capacity — fix v3

The previous attempt queried the entire ~18-km-radius corridor in one call and received a `502 Bad Gateway / server at capacity` from the public Overpass API. This was a **remote service error**, not a Python, CLIMADA, or unit-test failure.

Version 3 divides the waypoint axis into overlapping download segments at most **16 km** long, with a **9-km operational search buffer** around each segment. Those sizes are about data retrieval, **not** landslide runout. The graph is not simplified until after tile-merging (and it currently remains unsimplified), preserving road junction node IDs across tiles. Per-tile GraphML caching allows safe resumption after one failed request.

Run the offline unit tests before running the main script. If the download finishes, inspect `highway99_candidate_quality.json` and map overlays in QGIS. Treat the route as **unverified** until checked against an official BC road source.
